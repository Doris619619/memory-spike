## 方案中需明确的数值口径

- 文档的“6 × 3 × 3 ≈ 54 次”是组合示意。若包含 V2，其每个组合有两次调用，不能把组合数当实际调用次数。本实现使用允许省略 V2 的方案，避免该歧义。
- 文档中的“自建零边际成本、商用个位数美元”不当作当前平台报价。必须填写模型实际单价和价格来源；本工具按 usage 估算费用，实际账单、缓存折扣或特殊计价需另核对。
- 约 1.5k 输出 token 是估计，不是固定上限。配置显式记录上限（示例 4096，包含平台可能计入的推理 token）；截断单独记失败，不自动加大上限重试。
- 不验证注入效果、后台任务或收费闭环；不实施 §10.4 可选聊天效果冒烟。

## 准备实际模型配置

先把 `configs/models.example.json` 复制到仓库外。用平台当前的价格信息补全真实单价（本地也不能直接写 0）。

对 V0，应在明确的非正式能力探测中确认所选协议/网关支持 `json_schema`、`json_object` 或强制工具；记录探测日期、模型、请求模式、响应依据。失败不自动回退；确认不支持就填 `unavailable` 和证据说明。仅列出模型或普通 `OK` 调用成功不算 V0 支持证据。

## 运行日志恢复

`runs.jsonl` 先持久化 started，再调用一次模型，最后写结果。只有 started 的组合视为执行未知，恢复时跳过，不自动重发。`.running.lock` 防止两个进程同时消费组合。进程崩溃后先确认进程已结束并备份检查日志，再人工移除残留锁；损坏 JSONL 不自动截断。

运行目录的 `manifest.json` 保存当时样本、金标、模型参数和 prompt，用于复核请求内容；它不能证明同一模型服务以后能返回完全一致的答案。
