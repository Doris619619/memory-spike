# 个人记忆抽取质量评估 Spike 方案

版本：v0.2 · 2026-10-01
状态：方案稿，未执行。隶属 [产品设计](MEMORY_PRODUCT_DESIGN.md) / [后端实现方案](MEMORY_BACKEND_DESIGN.md) 的第 15.2 节"等待后续测试决定"中**最先执行**的一项：在写任何迁移、API 或 worker 之前，先用一天级成本验证"模型能否从 30 天真实聊天中抽出合格的个人记忆"。

本方案只设计评估方法，不修改任何业务代码、迁移或配置。spike 执行后的结论回写位置见第 11 节。

## 1. 为什么先做这个

整个 memory 模块的产品价值建立在单一假设上：**单次受限模型调用能从真实聊天里抽出准确、保守、不含敏感信息的稳定个人事实**。这个假设不成立时，其余全部工程（三张表、任务状态机、UniAuth 幂等账务、UI 管理页）都是在给一个产出垃圾的管道做精装修。

验证这个假设不需要任何基础设施：一段取样 SQL、一份 prompt、若干次模型调用、人工评分。成本约 2–3 人日。它同时产出三份可复用资产：冻结的 prompt v1（未来 `memorysvc` 的初始提示词）、取样脚本（`CollectSources` 的实现雏形）、失败模式目录（§14.3-16 评估集的种子）。

## 2. 要回答的六个问题

| # | 问题 | 对应决策 |
| --- | --- | --- |
| Q1 | 抽出的块有多少是"证据支持、泛化适度"的？ | 产品是否值得按现设计推进（Go/No-Go） |
| Q2 | 金标覆盖率多少——人认为该记的事实，模型抽到了几成？ | 栏目定义与输入上限是否合理 |
| Q3 | 结构化输出（V0）与纯 prompt 解析（V1）的格式失败率各是多少？ | "强制结构化输出是否升格为生成模型选型硬条件" |
| Q4 | 模型伪造 evidence ID 的频率？ | 服务端校验的必要严格度（后端 §6.3 的输入） |
| Q5 | 内容规则守不守得住——敏感信息、临时事项、材料误认各出现几次？ | prompt 内容规则是否需要修订或加程序过滤 |
| Q6 | 候选模型里哪个综合质量/成本最优？ | 后台生成模型选型（配置推荐值） |

## 3. 明确不在范围内

- 不验证注入效果（记忆放进上下文后回答是否变好）——那是产品 §14.7 的开/关成对测试，属于实施期验收，不属于本 spike。可选的廉价冒烟见第 10.4 节。
- 不验证计费、任务状态机、并发、发布事务——与抽取质量正交，且已有完整设计。
- 不做多次调用、自动修复、两段式流水线（除第 8 节的 V2 参照变体外）。一期"单次调用、失败不重试"是 P1 已固定决策，spike 沿用它，这样测出的失败率才是上线会真实发生的失败率。
- 不产出统计意义上的可靠比率。6 个样本是烟雾测试闸门，不是置信区间；它的职责是抓系统性失败模式，不是给"准确率 87.3%"这种数字背书。

## 4. 样本矩阵

数据来源：**明确知情同意的内部/测试用户**（对齐工作包 G"真实测试池、受控样本"），从其账号导出近 30 天聊天。没有真实样本的类别用合成会话补齐（合成样本只测规则遵守，不计入质量统计）。

| 样本 | 构成 | 验证目标 |
| --- | --- | --- |
| U1 轻度 | <10 会话、<100 条用户消息 | 无足够历史时输出近空、不虚构（对应产品 §4.3） |
| U2 中度 | 20–30 会话、混合主题 | 基准质量场景 |
| U3 重度 | >50 会话、超 500 条上限 | 抽样（非全量）输入下的质量下限；覆盖率衰减体感 |
| U4 渠道混杂 | 含子任务回调（`<agent-message>`）、校园会话、微信会话、Project 会话 | 取样排除逻辑：这些内容不得进入输入 |
| U5 敏感场景 | 聊天中出现过密码、证件号、住址、健康话题 | 内容规则：默认不提取（Q5） |
| U6 偏好丰富 | 明确说过语言/格式/称呼偏好的用户 | 最直接的价值场景：明确自述是否被可靠捕获 |

U4、U5 允许合成。U1–U3、U6 必须真实（合成聊天测不出真实语言习惯下的抽取行为）。

**数据纪律**（仓库规则的直接适用）：

- spike 工作目录放在仓库之外（如 `~/memory-spike/`），任何用户消息原文、块文本、金标条目不进 git。
- 报告进仓库的只有：prompt、方法、聚合数字、**改写或合成**的失败模式示例。
- 评估结束后删除样本转储；保留评分表（若含块文本，留在仓库外）。

## 5. 取样复刻（collect 脚本）

`scripts/memory_spike/collect.go`（拟新增，独立 `main`，只依赖 `go-mssqldb`，不接 GoFrame）——它就是后端 §5.1 `CollectSources` 的原型，spike 后可直接演进为正式实现。

**会话筛选**（已在当前代码验证为先例：`chat_v1_search_history.go:443` 的 `JSON_VALUE` 用法）：

```sql
SELECT chat_session_id, layout
FROM chat_session
WHERE user_id = @owner
  AND source = 'web'
  AND project_id IS NULL
  AND parent_session_id IS NULL
  AND ( JSON_VALUE(layout, '$.session_type') = 'chat'
        OR JSON_VALUE(layout, '$.session_type') IS NULL )
  AND updated_at >= @cutoff
```

旧 campus 会话（早于 `session_type` 机制、layout 为空）会通过 NULL 兼容混入——`displayed_msg_idx` 回溯到的 approach 行带 `approach_id`，按 `approach_id != 'campus-affairs-qa'` 二次排除。这个坑要专门测（样本 U4 含一条旧 campus 会话）。

**分支取样**（复刻后端 §5.2，参考 `load_history.go` 的 parent 回溯）：

1. 每会话读 `layout.displayed_msg_idx`，沿 `parent_idx` 回溯（有界深度 + 环检测）。
2. 只取 `role='user'` 行；`content` JSON 解出文本。
3. 排除合成消息：文本以 `<agent-message` 开头（旧数据唯一可用信号；诚实声明——真实 steering 无法与部分回调区分，保守排除）。
4. 消息时间窗按 `created_at`（content JSON 内），不是会话 `updated_at`。
5. 单消息截断 2,000 字符。

**上限**（对齐产品 §6.2 的测试起点）：≤50 会话（近优先）；≤500 条去重用户消息（每会话配额 15 条，余额按最近优先补足）；输入总量 ~24,000 token（脚本用 `字符数/2`（CJK）`/4`（拉丁）近似，正式实现换真实 tokenizer——spike 内统一近似即可比）。

**输出** `samples.jsonl`：每行一个样本 `{sample_id, window_start, session_count, message_count, sampled, messages: [{id:"m_NNN", session:"s_XX", date, text}]}`。ID 用短序号 `m_NNN`（省 token）；样本文件里 owner 只存 U1–U6 匿名标签，映射关系不落盘。

## 6. 金标标注（gold set）

每个真实样本（U1–U3、U6），标注者通读取样脚本输出的消息流（即模型将看到的同一输入），产出"一个人类助理会记住什么"清单：

| 字段 | 说明 |
| --- | --- |
| fact | 事实陈述（一句一事） |
| category | `auto`（可自动抽取）/ `sensitive`（规则默认排除）/ `temporary`（临时事项，排除） |
| evidence | 支持它的消息 ID |
| stability | 用户明确自述 / 多次出现的行为信号 / 单次弱信号 |

- 覆盖率（recall）**只在 `auto` 类上计算**；`sensitive`/`temporary` 类构成"禁止集"——模型抽到即违规，不计入漏报。
- 两个样本（U2、U6）由两人独立标注，度量标注者间偏差；其余单人标注。标注预计每样本 30–60 分钟。
- 金标条目含用户数据 → 只存在于 spike 工作目录。

## 7. 抽取 Prompt v0（核心资产）

以下为完整草案。中文撰写（团队可评审、可迭代）；若质量不达标，"中→英提示语言"列为下一轮测试变量。`{...}` 为运行时填充。

```text
你是个人信息抽取引擎，不是聊天助手。任务：从一位用户近 30 天的
普通聊天记录（仅含该用户本人的发言）中，抽取关于该用户的稳定个人
信息，形成候选记忆块。你的输出将由程序解析并校验，不会直接展示
给用户。

## 输入

多段会话按时间顺序排列；每条消息格式为 `m_NNN | 日期 | 会话s_XX | 文本`。
文本可能是多语言。部分消息可能内容很短（如"继续"），属于正常现象。

## 抽取规则

1. 只抽取关于【用户本人】的信息。用户消息中出现以下内容时，它们是
   待处理材料而非用户自述，禁止据此提取：用户请求翻译/改写/分析的外部
   文本、引用的文献或题目、角色扮演台词、粘贴的代码或报错、其他人的情况。
2. 只抽取【稳定】信息：长期沟通偏好、持续背景（工作/学习方向）、长期
   项目、持续兴趣。禁止抽取有截止日期或明确一次性的临时事项
  （如"下周三交作业""这周在感冒"）。禁止把单次任务要求泛化为长期偏好
  （"这篇用英文写"不等于"偏好英文回复"）。
3. 保守推断：用户明确自述（"以后都用中文回复""我是后端开发"）可直接
   抽取；仅从行为信号推断时，需要多次出现，且措辞降级
  （"多次讨论 React 相关话题"，而非"是 React 开发者"）。
4. 默认不抽取：密码/密钥、证件号、具体住址、健康细节、其他人的个人
   信息。即使输入中出现也不提取。
5. 每块只含一个事实，必须引用实际支持它的消息 ID。禁止引用输入中
   不存在的 ID，禁止编造 ID。
6. 同一主题出现相互矛盾的用户自述时，不要替用户选边：不写入任何
   一方，在 conflicts 数组中列出双方原文与证据。
7. 没有内容的栏目直接省略。总输出目标 400–800 个汉字；宁缺毋滥，
   没有足够证据就少写。

## 输出格式

只输出一个 JSON 对象，不输出任何其他文本、代码围栏或解释：

{
  "blocks": [
    {
      "section": "沟通偏好|背景与关注方向|持续事项",
      "text": "一句话事实",
      "evidence_ids": ["m_012"]
    }
  ],
  "conflicts": [
    {
      "topic": "主题",
      "statements": [
        {"text": "一方陈述", "evidence_ids": ["m_003"]},
        {"text": "另一方陈述", "evidence_ids": ["m_089"]}
      ]
    }
  ]
}

blocks 为空数组是合法输出（输入中没有可抽取的稳定信息时）。
```

设计对齐说明：

- 输出结构与后端 §4.2 内容块对齐，但**不含 `id`/`version`/`origin`**——块 ID 由服务端分配，`user_explicit` 由服务端判定不采信模型自报（后端 §6.3）。spike 不引入这些字段，避免评估阶段就固化错误契约。
- `conflicts` 对应产品 §6.2-6"无法消歧就不写入"，同时给 spike 提供冲突频率数据（观测项）。
- 栏目、长度目标、单事实一块均来自产品 §6.3。

## 8. 变体与模型矩阵

| 变体 | 构造 | 目的 |
| --- | --- | --- |
| V0 结构化输出 | 按 provider 能力强制 JSON：OpenAI-compat 网关用 `response_format`（支持 json_schema 则用 schema，否则 json_object）；Anthropic 用强制单工具调用 | 预期主路径；测 Q3/Q4 |
| V1 纯 prompt 解析 | 同一 prompt，无 response_format；解析取首个 `{` 到末个 `}` 再 Unmarshal + schema 校验 | 测不用结构化输出的失败率，决定 Q3 |
| V2 两段式（可选参照） | 第一次抽取后，第二次调用让模型审查第一稿（删除越权/过度泛化/敏感项） | 只测质量上限差值，为一期后的改进决策留数据；**不改变一期单调用决策**，时间不够直接砍掉 |

模型候选 2–3 个（Q6），约束：

- 至少一个自建/低成本模型（如 title/summary 工作马同款），至少一个商用强模型做质量参照。
- V0 仅在模型/网关真实支持强制结构化输出时运行；不支持则记为"V0 不可用"，这本身是选型数据。
- 每个模型记录：provider、apiType、是否支持 schema、实际单价。

**执行纪律**：每个（样本 × 变体 × 模型）**恰好调用一次**，失败即数据点，不重试。6 样本 × 3 变体 × 3 模型 ≈ 54 次调用，输入 ~26k token/次（消息 24k + prompt 2k），输出 ~1.5k token/次——自建模型零边际成本，商用模型总成本个位数美元。

`scripts/memory_spike/run.go`（拟新增，独立 `main`）：读 `samples.jsonl` + prompt 模板 + 模型配置，按变体构造请求，逐条调用并写 `runs.jsonl`（raw 输出、解析结果、校验结果、usage、延迟、失败分类）。仅从环境变量读 API key，不进代码。

## 9. 执行与评分

流程（总计 2–3 人日，串行约 1 个工作日）：

| 步骤 | 工作量 | 产出 |
| --- | --- | --- |
| 1. 招募 6 个同意样本 + 跑 collect | 0.5 人日 | `samples.jsonl`，矩阵覆盖核对 |
| 2. 金标标注（U2/U6 双人，其余单人） | 0.5–1 人日 | gold set |
| 3. 跑变体矩阵 | 0.5 人日（无人值守） | `runs.jsonl` |
| 4. 评分与汇总 | 0.5–1 人日 | 评分表 + 报告草稿 |
| 5.（允许一次）prompt 修订后重跑受影响组合 | +0.5 人日 | v1 prompt |

**块级评分表**（人工，每块一行）：

| 维度 | 判定 | 说明 |
| --- | --- | --- |
| E1 证据有效 | 二值 | 引用 ID 存在于输入，且该消息内容确实支持该陈述（Q4 的分母之外——E1 是"引用了但内容不支持"） |
| E2 ID 伪造 | 二值 | 引用了输入中不存在的 ID（Q4 直接度量） |
| F1 事实正确 | 三值 | 正确 / 过度泛化 / 错误（对照金标或标注者判断） |
| S1 稳定性 | 二值 | 稳定事实 vs 临时事项（临时=违规） |
| X1 敏感违规 | 二值 | 含规则 4 禁止类别（违规） |
| M1 材料误认 | 二值 | 材料/引用/角色扮演被当成用户自述（违规） |

**运行级指标**（每 (样本×变体×模型) 一行）：块数、精确率（无任何违规的块占比）、E1 通过率、ID 伪造率、recall（命中金标 auto 类的比例）、冲突正确延迟数、格式失败分类计数（非 JSON / schema 不符 / 空输出）、输入输出 token、延迟、成本。

聚合表：模型 × 变体 → 各指标均值 + 最差样本。

## 10. 判定标准（Go/No-Go）

阈值是方向性初判线（6 样本无统计效力），最终由产品与研发在评审时冻结。

### 10.1 阻断项（P0）

- 任一真实样本出现 X1（敏感违规）且非用户明确要求记住 → 内容规则失败：先修 prompt 规则 4 措辞，修不住则一期增加程序侧敏感过滤（后端 §6.3 校验链加一环），并重跑 U5。
- V0 格式失败率 > 2% → 该模型不适合作为结构化输出生成模型，换模型。
- V1 与 V0 失败率同时 > 8% → prompt 格式约束失败，修订后重跑；仍失败则 No-Go。

### 10.2 质量线（P1）

- 块精确率 ≥ 0.80（含 F1 泛化适度）
- E1 证据支持率 ≥ 0.90
- recall ≥ 0.60（对金标 auto 类）
- 两轮 prompt 迭代后精确率仍 < 0.70 → **No-Go 自动抽取**：一期降级为产品 §4.3 的"用户描述创建"为主路径（该路径已设计、依赖同一受限调用但输入是用户明确指令，抽取难度低一个量级），自动整理延后并重新评估。这是 spike 的明确退路，不是失败——它把三端三个月的投入从错误赌注上撤下来。

### 10.3 决策输出

- V1 失败率 > 8% 且 V0 < 2% → 确认"强制结构化输出是生成模型选型硬条件"，回写后端 §6.2，把该句从"Provider 支持时使用"升格。
- recall 0.4–0.6 区间且失败集中在"多次出现的行为信号" → 记录为已知边界，不阻断；栏目标签措辞是否引起漏报单独分析。
- U3 重度样本精确率显著低于 U2 → 输入抽样策略（会话配额、近优先）进入实施期参数测试清单。

### 10.4 可选冒烟（+0.5 人日，非本 spike 范围）

抽取质量达标后，把冻结的 memory.md 手工拼进一个测试会话的 system 上下文，用 3–5 个偏好相关问题人工对比开/关回答。只回答"有没有可感知的价值"，不替代产品 §14.7 的正式对照验收。

## 12. spike 自身的已知局限

1. **样本量小**：~100–200 个块足以抓系统性失败，不足以宣称精确率到个位数百分比。灰度期（工作包 G）仍需复测。
2. **测试用户偏差**：工程师聊天偏技术、偏短句；真实学生/教职工用户的表达密度不同。金标覆盖率对该偏差敏感。
3. **单人标注为主的金标**：标注者本身会漏——recall 是下界估计；双人样本用于度量该偏差量级。
4. **近似 token 计数**：脚本用字符近似，与真实 tokenizer 差 ~10–20%；影响的是上限触发的精确位置，不影响质量结论。
5. **旧数据合成消息识别**：靠 `<agent-message` 前缀保守排除，真实 steering 输入会被误排除——这是设计已接受的覆盖率损失，spike 里表现为 recall 略偏低，评分时注意不要把该项误记为模型缺陷。

## 13. 与仓库验证约定的关系

本 spike 不触发 `make fmt/test/lint` 与迁移检查（不触碰业务代码）。`scripts/memory_spike/*.go` 为独立模块（自带 `go.mod`，不 import 主模块），不进 CI；其存在理由是可复现性——跑批参数（模型、变体、prompt 版本哈希）全部落在 `runs.jsonl` 里，评审时可以回放任何一次调用。
